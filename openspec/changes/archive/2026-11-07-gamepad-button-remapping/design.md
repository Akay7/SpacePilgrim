# Design

## Context

Gamepad input reaches the game through Kivy's `on_joy_button_down/up`, `on_joy_axis` and `on_joy_hat` window events. Each carries only `stick`, the SDL joystick **instance id**; Kivy exposes no pad name or GUID. `_on_joy_button_down/up` look the button id up in the module-level `JOY_BUTTON_ACTIONS` (desktop and Android tables with different numbering: Android also reports the D-pad as buttons 11-14 and Back/Start as 4 and 6, desktop as 6 and 7). The result goes through `_input(source, action, pressed, device)`, which routes `up/down/left/right/fire/back` to menus, popups, the join screen or the ship. Axes 0 and 1 produce `left/right/up/down`; other axes are ignored today.

Thrust is binary: `Spaceship.update` sets `speed = 3` while `thrust` is on and otherwise decays it by 0.98. `ControlsManager.press/release/_apply` turn the held actions into `thrust_on/off` and turning.

On Android `PadWatcher` already loads `libSDL2.so` through ctypes to open pads. On desktop Kivy's bundled SDL2 library is loaded into the process but is not given a ctypes handle.

Keyboard rebinding is the model to follow: `KeyBindings` (defaults, `rebind` returning an error message, `reset`, versioned JSON in `user_data_dir`, validation falling back to defaults), `KeyboardSettings` (a `ButtonColumn` with `waiting`, `handle_key`, `refresh(message)`), and `_on_key_down` handing the key to the settings page while it waits. See proposal.md for scope.

## Goals / Non-Goals

**Goals:**
- Rebind thrust and fire per pad model with the same behaviour as keyboard rebinding: replace, conflict refusal with a message, cancel, persist, reset.
- Optional analog thrust trigger per pad with proportional power.
- Keep Back/Start, stick and D-pad fixed, and menus on the standard buttons, so no binding can lock the player out of menus or the game or change how they work.
- Defaults and existing tests keep working.

**Non-Goals:**
- Layouts for two pads of the same model, remapping sticks/D-pad/Back, triggers for fire, button glyphs per brand, analog thrust for keyboard/touch, engine sound volume following the trigger.

## Decisions

1. **`PadIdentity`: name and GUID per instance id.** A small helper wraps the SDL library (`SDL_JoystickFromInstanceID`, `SDL_JoystickName`, `SDL_JoystickGetGUID` plus `SDL_JoystickGetGUIDString`) and answers `identity(stick)` with a stable string like `"<guid>"` and a display name, and `connected()` with the identities of the pads present (via `SDL_NumJoysticks` / `SDL_JoystickNameForIndex` / `SDL_JoystickGetDeviceGUID` / `SDL_JoystickGetDeviceInstanceID`, so no pad has to be opened). A stick that sends events but cannot be identified is listed on the page as "Unidentified gamepad", which makes the session-only layout reachable. On Android it reuses the `libSDL2.so` handle that `PadWatcher` loads; on desktop it opens the SDL2 library Kivy already loaded. Any failure (library not found, missing symbol, unknown id) yields `None`: the pad is "unidentified" and uses the defaults, with session-only changes. Tests inject a fake identity helper, so none of this needs real hardware. *Alternative*: key layouts by pad number (Gamepad 1..4) — rejected by the user in favour of following the physical pad; it would swap layouts when connection order changes.
2. **`GamepadBindings`: one profile per identity.** Profiles map identity -> `{"buttons": {"up": [...], "fire": [...]}, "trigger": None | {"axis": n, "rest": r, "full": f}}`. Defaults are the existing `JOY_BUTTON_ACTIONS` of the running platform. API: `profile(identity)` (profile or defaults), `action_for(identity, button)`, `label(identity, action)`, `rebind(identity, action, button)` (error message or `None`), `bind_trigger`, `reset(identity)`, `load()/save()`. Pads of the same model share an identity, hence one profile (stated and accepted: they cannot be told apart). *Alternative*: mutate `JOY_BUTTON_ACTIONS` in place — rejected, tests and platform selection rely on the constants staying as defaults.
3. **Fixed inputs stay**: Back (`4`, `6` on Android; `6`, `7` on desktop) and the Android D-pad buttons (`11-14`) stay in a fixed `JOY_FIXED_ACTIONS` split out of the current tables, checked first. These ids are the reserved set for button rebinding. Axes 0 and 1 (left stick) and hats are reserved for trigger binding. *Alternative*: keep A as an un-rebindable "confirm" — rejected: the fixed D-pad plus Back already guarantees navigation, and a button of each pad always fires.
4. **Rebind rules** mirror the keyboard: a new binding replaces all buttons of the action (A and X collapse to one button), conflicts are checked within the profile only (the same button may mean different things on different pads), messages `Already used for Thrust` and `That button is reserved`.
5. **Capture flow**: `GamepadSettings` is a `ButtonColumn` with `waiting` (`'up'`, `'fire'` or `''`), `pad` (identity being edited) and `handle_button(stick, button)` / `handle_axis(stick, axis, value)`. In `_on_joy_button_down` and `_on_joy_axis`, if a settings page is waiting, the event is consumed there before normal routing: events from sticks whose identity differs from the edited pad are ignored; Back buttons cancel; any other button is bound or refused. `_input` already returns early for pad input while `self.settings.waiting` is set, so stick and D-pad movement needs no extra handling; the matching button-up is dropped by `_inputs_down` bookkeeping. Escape cancels through the same generalisation of `handle_key` used for `KeyboardSettings`.
6. **Thrust is one entry for a button or a trigger**: while the page waits for Thrust, a button press binds the button (clearing a bound trigger) and a pulled trigger binds the trigger (the buttons stay stored but are ignored, and no longer conflict with Fire); while it waits for Fire, axes are ignored. Axes 0 and 1 (the stick) are always ignored while waiting, so nudging the stick neither binds nor cancels. A bound trigger shows as "trigger (axis N)" in the Thrust label. *Alternative*: a separate "Thrust trigger" entry with its own clear action — rejected by the user in favour of one element.
   **Trigger capture and calibration**: when the page starts waiting for Thrust it stores the current value of each axis of the edited pad as that axis's *rest*, read from SDL (`SDL_JoystickGetAxis` through `PadIdentity.axes`; Kivy has no axis query). An axis SDL did not report rests at 0. The first axis (not 0 or 1) that moves more than half of its range from rest is bound with `rest` and `full` (the extreme in the direction it moved). This handles drivers where triggers rest at -1 and ones where they rest at 0, and the Android and desktop numbering differences, without a table. The raw value is normalised `(v - rest) / (full - rest)`, clamped to `[0, 1]`, with a dead zone of 0.1 mapped to 0 and the remainder rescaled to 0-1. *Alternative*: hard-code axis 4/5 — rejected, numbering differs by driver and platform.
7. **Analog thrust level**: `Spaceship` gets `thrust_level` (0-1, default 1) used as `speed = 3 * thrust_level` while `thrust` is on, and `ControlsManager` gets `set_thrust(level)` that sets the level and calls `thrust_on` above 0 or `thrust_off` at 0 (so the engine sound plays whenever a ship thrusts at any power, as before). `press('up')` keeps meaning level 1. A bound trigger calls `set_thrust(level)` for the ship of the pad's player only. Keyboard, touch and buttons are unchanged. Because the level scales speed, not acceleration, a half pull gives half of the cruising speed, as the proposal says "power".
7b. **Layouts apply in game only**: `_on_joy_button_down` uses `GamepadBindings.action_for` while `_in_game`, and the platform's standard `JOY_BUTTON_ACTIONS` (A/X activate, B/Y up, Back, Android D-pad) everywhere else, for every pad. So remapping never changes navigation, a remapped button does nothing in menus, and the join screen hint "A ready" stays true. The press-time action (decision 9) keeps a press and its release together when the screen changes in between. *Alternative*: remapped Fire also activates menus (the first design) — rejected: it changes standard navigation and makes menus depend on the layout.
7c. **Sticks give thrust power too**: `stick_level(push)` (dead zone 35% of the range, linear to 1 at the edge, the same constant the on-screen `Joystick` already used as its threshold) turns how far up a stick is into 0..1. `ControlsManager.set_thrust(level, source)` keeps one level per analog source (`'trigger'`, `'stick'`) and thrusts with the strongest; a held thrust key or button is still level 1. The on-screen `Joystick` stops pressing `'up'` and reports `stick_level(dy)` through `ScreenButtonsLayout.thrust`; turning stays on/off at its 35% threshold. For a gamepad, axis 1 in the game calls `_stick_thrust` (and no longer produces `'up'`/`'down'`, which only menus read) while axis 0 keeps turning at the 0.5 dead zone and the D-pad stays digital. Pause clears every source. *Alternative*: thrust power only for the on-screen joystick — rejected by the user.
8. **Trigger replaces the button for that pad**: while a profile has a trigger, `action_for` maps that pad's thrust buttons to nothing, and axis events from the trigger feed `set_thrust`. Axis events go through a dedicated path (not the on/off `_input`) because they carry a continuous value; join/leave/menu routing is unaffected since a trigger only matters in a running game for a joined pad (`_controls_of(device)` decides, as for buttons).
9. **Press-time action for buttons**: the `_inputs_down` key stays `('button', stick, button)`, and the action chosen at press is remembered (`self._button_down[(stick, button)]`) so the release uses it even if bindings changed meanwhile and no ship is left thrusting or firing.
10. **Page and navigation**: `SettingsScreen` gains a "Gamepad buttons" entry (height grows to fit); `GamepadSettings` rows are the pad selector, Thrust, Fire, Reset to defaults, Back and a message label, shown via `show_gamepad_settings()`. The selector cycles through `PadIdentity.connected()` (one entry per model); with no pad it shows "No gamepad connected" and the binding rows are disabled. Navigation and activation reuse `ButtonColumn.move/activate`, so touch, keyboard and gamepad all work, and a pad's fire button (remapped or not) activates entries.
11. **Labels**: button id -> name through a small table (0 A, 1 B, 2 X, 3 Y), else `Button N`. The trigger shows as `Axis N`.
12. **Persistence**: `gamepad_buttons.json` in `user_data_dir`, `{"version": 1, "pads": {identity: {...profile...}}}`, written after every change/reset of an identified pad. Load validates each profile (known actions, non-empty int lists, no bools, no reserved ids, no id used twice, trigger with numeric `rest`/`full`, `rest != full`, axis not 0 or 1); an invalid profile is dropped (defaults) and a malformed file drops everything. `OSError` on save is swallowed so the session keeps its bindings. The file is per device, so platform-specific numbering needs no migration. Unidentified pads use an in-memory profile that is never saved. *Alternative*: store inside `keybindings.json` — rejected: that file is versioned and migrated for keyboard sets, and keyboard reset must not touch gamepad bindings.

## Risks / Trade-offs

- [SDL cannot be reached through ctypes on some desktop builds] → pads are unidentified: defaults apply, the page still works for the session, nothing breaks.
- [Android and desktop number buttons and axes differently, so a binding is only meaningful on the device where it was made] → the file lives in that device's user data; trigger capture records axis and travel instead of assuming numbers.
- [Some drivers expose triggers as buttons, or as a single axis shared by both triggers] → a trigger that arrives as a button can be bound as the Thrust button; a shared axis pulls in one direction per trigger and only the binding direction is used.
- [Pads of the same model cannot have different layouts] → accepted and stated in the spec; different models can.
- [A noisy axis resting off-centre triggers the capture or leaves a small constant thrust] → the half-range threshold in capture and the 0.1 dead zone at play.
- [A rebind collapses A and X into one button] → same as the keyboard; Reset restores both.
- [Player binds Fire to a button held while the page waits] → only a fresh press binds; the press that selected the entry is dropped by `_inputs_down`.
- [Rewiring `ControlsManager` for a thrust level could change keyboard/touch thrust] → level defaults to 1 and the existing tests for thrust and engine sound must keep passing.

## Migration Plan

Additive: without `gamepad_buttons.json` the defaults reproduce today's behaviour exactly for every pad. Rollback is deleting the new file or reverting the code; no other stored data changes.
